Project Context — the web GUI

This is the memory of the system, and it comes with its own web GUI. It runs as a container and serves a browser interface at the container's address — for example http://localhost/ui. From there you manage the projects the agent knows about, inspect what it has indexed, and watch what it is doing — all on infrastructure you control.

Open the GUI

The Project Context runs as a container. Once it is up, open a browser on the same machine and go to its address — the GUI is served under /ui:

  1. Point your browser at the container, for example http://localhost/ui.
  2. You land on Projects — the list of everything the agent knows about.
  3. The sidebar on the left takes you to the rest, grouped as Projects (New Project, Select Project, Context Engine), Tools (MCP Tools), RAG (Settings, Collections) and Settings (Parameters, Logs).

Projects

A project is a folder the agent is allowed to understand and work in. The start page of the GUI lists every project currently registered with the server.

Select a project

Pick the project you want to work with either by clicking its card or from the selection list.

Register a new project

Registering a folder makes it part of the agent's memory. Along with the project itself you define its specs — a description of what the project is — which the agent reads as context before it works in that project.

Edit a project and its specs

Everything you set at registration can be changed later. Editing a project lets you redefine:

  • the project path,
  • the Git repository,
  • the correlations with other projects (see below),
  • the specs — Markdown is allowed.

Correlate projects

When one project is part of other projects — a library used by a backend, for example — you can correlate them. Correlations give the agents a map of the other places worth looking, so an agent working in one project knows which related projects may hold the rest of the answer, and which peers to coordinate with over ACP.

Learnings

Learnings are the notes agents save about a project as they work — decisions, pitfalls, verified workflows. Search all recorded learnings by keyword and filter them by category.

Recorded changes

Every edit an agent records is kept as a change. The last 250 changes can be listed, filtered by category or searched by keyword — so you can see a project's recent history without opening Git.

Context Engine

The Context Engine is what the agent consults first on every task — an indexed model of the project's structure rather than a blind file read. It knows the project's symbols (functions, classes, methods), where each one lives, how they relate, and which changes were recorded recently. Here you can run the same lookups the agent does — find a symbol or ask a question about the code — and see exactly what the agent would get back: the file, the line range and the relevant source excerpt.

The context engine is the source of truth for a project's structure. It is how the agent understands how pieces fit together before it edits anything — which keeps its changes grounded in the real codebase rather than guesses. Each recorded change re-syncs the index, so the next answer reflects what was actually edited.

RAG Settings

Retrieval is backed by a self-hosted RAG server. Your project's code is indexed into it with chunks built around whole symbols, so a search result is a complete function or class rather than an arbitrary range of lines. Edits are stored as before/after snapshots. On top of your own code, the RAG can hold external documentation, so the agent looks up the real docs for a framework instead of relying on what it remembers.

RAG → Settings opens RAG Sources & Configuration, an editor for the RAG server's config/sources.yaml. This file lists the documentation sources the RAG crawls on a schedule (every 6 hours by default).

Only two top-level keys are accepted. If the file contains anything else, the RAG server rejects it:

  • github — a list of repositories to index:
    • repo (required) — the repository as owner/name, for example home-assistant/developers.home-assistant.io.
    • file_types — the file extensions to pull from the repository. Default: md and py.
    • collection — the collection the content is stored in. Default: github.
  • urls — a list of web pages to crawl:
    • url (required) — the page the crawl starts from.
    • depth — how many levels of links the crawler follows from that page. Default: 1. Each extra level can add many more pages, so raise it only for documentation sites where the useful content is a few clicks deep.
    • collection — the collection the content is stored in. Default: web_docs.

Collection names are up to you. A collection is created the first time something is stored in it, so grouping sources by topic (for example ha_docs, python_docs) keeps each set of docs separate. A fresh install starts with an empty sources.yaml.

To change the sources:

  1. Reload from RAG loads the file currently on the RAG server.
  2. Edit the YAML, then click Validate YAML. Save to RAG stays disabled until the file passes validation.
  3. Tick Re-scan all sources after saving if you want the new sources crawled right away instead of at the next scheduled scan. This is slower.

RAG → Collections is in the menu but not live yet. It will list the collections and what each one holds.

Everything here is computed and stored on infrastructure you control: the full codebase stays in your RAG instance, and the agent retrieves the chunks and embeddings it needs to work. When you configure a hosted model, that retrieved context is what gets sent to it — which is why we recommend a fully local setup (with Ollama) when you want nothing to leave your environment at all.

MCP Tools

Enable or disable each tool the MCP server exposes. Only enabled tools are shown to the agent when it first invokes the server through the Gateway — so you decide exactly which actions an agent can see and use.

MCP parameters

Under Settings → Parameters you set the server's environment. Values are saved to settings.json in the persistent data volume and take precedence over environment variables, which in turn override the built-in defaults. Restart the MCP container after saving so every service picks up the new values.

  • PyCharm RAG FileWatcher URL (MPC_FILEWATCHER_URL) — where the server notifies the file watcher after a recorded change, so the file is re-indexed right away. Normally the live watcher is found automatically; this is the fallback.
  • Host projects root (MPC_HOST_PROJECTS_ROOT) — the folder on the host that holds your projects, mounted read-only into the container so the server can read and index them. Changing the mount itself means recreating the container.
  • RAG server base URL (RAG_BASE_URL) — the RAG backend used for search, the Context Engine, ingestion and snapshots. If it's wrong, the Context Engine and semantic search stop working.
  • HA with Samba — server IP, share (default config), username, password, component name and port (default 445) used by the Home Assistant tools to deploy, back up and read a custom component over SMB. The component name can be overridden per project.

Secrets such as the Samba password are shown masked; leaving the mask in place keeps the stored value, so saving the form never wipes or exposes a secret.

Keeping the index honest — the file watcher

An index is only useful if it matches the code on disk. The Project Context stays in sync with a companion file watcher that runs on each of your machines:

  • When a file changes and the change is recorded, the watcher on that machine uploads the exact local file.
  • The store re-indexes it, so the next query reflects the change.
  • Because each watcher reports its own address, this works even when the editing machine and the server are different hosts.

The RAG File Watcher is on the JetBrains Marketplace — view the listing or install it directly from your IDE.

Logs

The Logs tab shows what the server is doing in real time — registrations, indexing activity and queries — so when something looks off, you can see why without leaving the browser.

Hardware — indexing quality follows the GPU

Turning code into a searchable index is the compute-heavy part, and it runs best with a GPU. IDEAgent runs on CUDA-capable NVIDIA machines and on boxes with shared-memory GPUs — laptops and Macs — but the two are not equal:

  • NVIDIA (CUDA) is the recommended and tested configuration, and gives the best indexing quality.
  • Shared-memory GPUs (Dell laptops, Macs) work, but indexing quality degrades compared to CUDA hardware.
  • More VRAM and system RAM give more headroom for larger projects, especially when a local Ollama model shares the same machine.

RAG-Server Docker Images

The RAG server uses vector databases and therefore embedding models. For speed and embedding quality, larger models are required. GPUs can batch embed 1,855 files in half or a quarter of the time of a CPU.

Choose the Docker image tag corresponding to your host hardware:

Mac / no GPU
latest
NVIDIA (Linux, Windows)
latest-nvidia
AMD (Linux, RX 7000/9000)
latest-amd

For complete instructions on connecting the RAG server to your IDE, follow the Setup Guide.

Privacy by construction

Indexing and storage stay on infrastructure you control: indexing runs on your own hardware, the collections live in a store you host, and retrieval returns only the small, relevant slices the agent needs. The file watcher may upload a changed file to the RAG server, and that server can be a different host from the editing machine — but both run inside your own infrastructure (for example, our container installed in your environment), so the full codebase is never transmitted to an external model provider — only the retrieved slices are sent, and only if you configure a hosted model. Paired with a local Ollama provider on the Gateway, no code or context leaves infrastructure you control at all.
