MCP Server, Context Engine & RAG

This is the memory of the system. The MCP server implements the Model Context Protocol and exposes a context engine over a self-hosted RAG backend, so the gateway's agent can find exactly the right code and project knowledge for each request — without ever shipping your whole codebase to a third party.

What the context engine does

The context engine is the agent's first move on any task: instead of blindly reading files, it queries a real, indexed model of the project. It exposes three focused actions:

  • find_symbol — locate a named symbol (function, class, method) or search semantically with a natural-language query, and see its definition, source and neighbours.
  • get_context — assemble a rich answer for a query: relevant entry-point files, recorded project learnings, full file context and recent changes, in one call.
  • sync_rag — push the latest state of a file into the index so the next query reflects reality.
The context engine is the source of truth for the project's structure. It is how the agent understands how pieces fit together before it edits anything — which is what keeps changes grounded in the real codebase rather than guesses.

The connection to the RAG

The context engine is backed by the self-hosted RAG server (port 5810). The RAG is where retrieval actually happens:

  • Local embeddings. Source code and knowledge are embedded with a local sentence-transformers model — no embedding API call leaves your machine.
  • Symbol-aware chunking. Code is chunked around top-level symbols, so a retrieved snippet is a meaningful unit (a whole function or class) rather than an arbitrary line range.
  • ChromaDB vector store. Chunks live in a local ChromaDB collection; a query returns the most similar snippets by cosine similarity.
  • More than code. The RAG also stores project learnings, file snapshots (before/after versions of changes) and scraped documentation, so get_context can weave history and docs into its answer.

The MCP tools call the RAG over REST with short timeouts and graceful degradation: if the RAG is briefly unavailable, the rest of the MCP server keeps working.

Hardware — the embedding phase wants a GPU

Embedding is the compute-heavy part of the RAG. Every indexed file and every query has to be turned into vectors by the local sentence-transformers model, and that step runs fastest on a GPU. It will run on CPU, but on a large codebase re-indexing and query latency are noticeably slower.

  • NVIDIA is recommended and tested. The embedding phase has been validated on NVIDIA (CUDA) hardware, so an NVIDIA GPU is the recommended configuration for the RAG host.
  • CPU still works. No GPU is required to run — embeddings simply fall back to CPU, at a performance cost that grows with project size.
  • More VRAM + RAM = more headroom. A GPU with more VRAM (and a host with more system RAM) lets the RAG index larger projects and keep more in memory, which matters most when the RAG and a local Ollama model share the same machine.
Everything stays on-device: putting an NVIDIA GPU on the RAG host keeps embeddings fully local and fast — you get the privacy of local retrieval without paying for it in latency.

Keeping the index honest — the file watcher

An index is only useful if it matches the code on disk. IDEAgent keeps them in sync with a companion file watcher plugin and a record_change flow:

STEP 1
Edit
The agent (or you) changes a file and records it via record_change.
STEP 2
Resolve
The MCP server finds the right machine's watcher from a live registry the RAG keeps.
STEP 3
Upload
That machine's watcher uploads the exact local file to the RAG.
STEP 4
Re-index
The RAG re-embeds it, so the next get_context reflects the change.

Because the watcher runs on each machine and reports its address to the RAG, this works even when the editing machine and the server are different hosts — no hardcoded IPs, and stale watchers are ignored.

The web UI

In progress. A web UI for the MCP server is under active development. It will make the context engine and RAG inspectable outside the IDE — browsing indexed projects, symbols, learnings and recent changes, and running retrieval queries directly. Until it ships, the engine is used through the MCP tools driven by the gateway.

Privacy by construction

Everything here is local: embeddings are computed on-device, vectors live in a ChromaDB you host, and retrieval returns only the small, relevant slices the agent needs. The full codebase is never transmitted anywhere. When paired with an Ollama provider on the gateway, no code or context leaves your infrastructure at all.
